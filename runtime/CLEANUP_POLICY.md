# Cleanup policy для `runtime/` и `statistic/`

Tech debt audit 2026-06-21, находки #11/#12. Зафиксировано как процессное
правило (не код) — `runtime/` и `statistic/` смешивают накопительные данные
с одноразовыми артефактами control-series прогонов.

## Что НАКОПИТЕЛЬНОЕ — НЕ удалять

- `runtime/autonomous_tester/decisions.jsonl`, `failures.jsonl`, `summary.json`
  — история всех прогонов автотестера, нужна для трендов/дашборда.
- `runtime/learning_cases.jsonl` — обучающие случаи для Learning Loop.
- `statistic/<project>/runs.jsonl`, `summary.md`, `run_*.json` — закоммиченная
  история control-series (осознанная политика — полный аудит-трейл).

## Что ОДНОРАЗОВОЕ — безопасно удалять после прогона

- `runtime/autonomous_tester/clones/<project_id>/` — клон репозитория для
  одного прогона.
- `runtime/<project_id>/` (basename клонированной директории) — рабочее
  состояние пайплайна для ОДНОГО прогона (`.webbles/`, `needs_review/`,
  baseline.json, memory.json).
- `webles_config.json.tester_bak` — бэкап конфига на время прогона
  (восстанавливается через `trap` при нормальном завершении; если прогон
  прерван аварийно — может остаться, тогда восстановить вручную:
  `cp webles_config.json.tester_bak webles_config.json && rm webles_config.json.tester_bak`).
- `chat/snapshots/<hash>.json` — новые файлы, появившиеся ТОЛЬКО во время
  тестового прогона (НЕ те, что уже были в git до прогона — их трогать нельзя).
- `.webbles_tmp_*` — временные файлы пайплайна, должны самоудаляться, но
  иногда остаются при убитых процессах.

## Когда чистить

После КАЖДОГО ручного/диагностического прогона (control series, ad-hoc
тестирование фиксов) — сразу после анализа результатов, не откладывать на
потом. Автоматический skill `webbles-autonomous-tester` уже делает это сам
(ШАГ 5 в его инструкции) для прогонов через сам skill — эта политика
актуальна для РУЧНЫХ прогонов мимо skill'а (как в большинстве сессий аудита
и ревалидации фиксов).

## Почему не автоматизировано полностью

Принудительная авто-чистка ВСЕГО `runtime/` по расписанию рискует задеть
накопительные файлы при ошибке в правиле различения "одноразовое vs
накопительное" — ручная проверка перед удалением (как делалось в каждой
сессии этого проекта) безопаснее, чем cron-скрипт без присмотра.
